# S0.5 移植清单：把 fork 的 Volta 解码注意力搬进本分支

> 目标：在本分支（上游 sm_70 线）上复现 fork 的 **INT8 small-T decode attention v2**，让
> Qwen 家族在上游线上从当前 **14.8 tok/s** 提升到接近 fork 的 **62.1 tok/s**（见
> [baseline](baseline-2026-10-12.md)）。这一步只动注意力，不动模型层，是整条正向路线的可行性验证。

## 2. 落点：上游对应结构

上游**已有**自己的 Volta 注意力（PR #58 引入）：

```
src/ops/softmax_attention/dense/causal_cache/
  small_t.cu               594 行  ← 小 T 解码启动器 + 统一 route 分发
      #include "…/small_t_sm70.cuh"      (在 #if defined(NINFER_SM70) 下)
      #include "…/small_t_i8_launch.h"   ← 上游特有的按 shape 生成启动器
  small_t_sm70.cuh                 ← 上游的 Volta 解码内核
  small_t_i8_launch.{cuh,h}        ← 上游特有
  small_t_i8_w{1..8}_h{16,24}_{append,cached}.cu   ← 上游按 shape 生成的一组实例
  prompt_sm70.{cu,h}      337+…    ← 上游的 Volta prefill，使用 small_t_sm70.cuh
  prompt_i8_fast.cuh               ← 用 ops/common/sm70_emulation.cuh 的 mma 模拟
```

fork 的分发写法（`small_t.cu` 内，`#ifdef NINFER_VOLTA_BUILD`）：

```cpp
#include "…/small_t_bf16_volta.cuh"
#include "…/small_t_i8_volta.cuh"
#include "…/small_t_i8_volta_v2.cuh"
// … 在 partial 路径里直接改用 *volta* 变体，注释写明：
//   "the DFlash2 merge dropped this reroute and sent BF16 decode …"
//   "fork's independent Volta SIMT int8 producer"
```

上游的门控宏是 `NINFER_SM70`（以及设备侧 `NINFER_SM70_DEVICE`），fork 用的是
`NINFER_VOLTA_BUILD`。**移植时必须统一到上游的宏**（不要新引入宏，避免与上游 merge 冲突）。

## 3. 移植步骤（每步可编译、可回退）

| 步 | 动作 | 检查点 |
|---|---|---|
| 0 | 在 `gemma` 分支建立构建循环（见 [PLAN](PLAN.md) §6「内核开发的增量循环」） | `ninja ninfer-serve` 干净通过 |
| 1 | 把 `small_t_i8_volta_v2.cuh`（498 行）原样拷入，仅**重命名宏**与头路径；先不做任何分发改动 | 能编译成对象（允许未使用告警） |
| 2 | 在 `small_t.cu` 里按上游的 `NINFER_SM70` 分支挂接 v2 作为 int8 解码路径（对齐上游的 route/envelope 结构，而不是照抄 fork 的 `NINFER_VOLTA_BUILD` 块） | 编译通过 + `ninfer_bench`/推理跑通 |
| 3 | 移植 `db947f95`（fp16 PV 累加链）与 `6856d323` 的增量；对齐 `geometry.cuh` 的长上下文缩放（`c58a92ba`） | 同上 |
| 4 | 可选：`small_t_bf16_volta.cuh`（bf16 KV 路径） | 同上 |
| 5 | **A/B 验收**（见 §4） | decode 达 fork 量级；贪心输出逐 token 一致 |

**必须注意的接口差异**（第 1、2 步的实质工作）：

* 上游有 `small_t_i8_launch.{cuh,h}` 与按 shape 生成的
  `small_t_i8_w{1..8}_h{16,24}_{append,cached}.cu`（fork 没有），v2 要么接进这套按 shape
  的实例化，要么在上游的 route 表里新增一条 sm_70 优先级更高的 route。
* `geometry.cuh` 两侧不同（fork 28 行 / 上游 18 行），模板参数与 `TokenTile` 的含义需要对齐。
* 上游 `small_t.cu` 引了 `ops/common/device_route.h`、`ops/kv_cache/d256_profile.h`
  等 fork 没有的层；v2 内核若直接触碰这些结构，改动面会扩大。

> 保守预期：第 1–2 步（编译 + 挂接）约 1–2 天；第 3–4 步各 0.5–1 天；第 5 步验收 0.5 天。
> 若第 1 步就发现 v2 依赖 fork 独有的 KV/route 结构，则应缩小目标为
> "只移植 v2 的**算法**（key-split 8-warp `Bc=64` + `byte_perm` int8→fp16 反量化 + fp16 PV 累加链）
> 写进上游的 `small_t_sm70.cuh`"，而不是搬整个文件。

## 4. 验收标准

1. **正确性**：同一 prompt、`temperature=0`（贪心）、`--spec none`，上游线移植前后的输出
   逐 token 一致；再与 fork 在同参数下对比。
2. **数值**：上游自带 `tests/` 中的注意力测试（`ninfer_*_attn*`）在 `NINFER_SM70` 构建下通过。
3. **性能**：用 [`bench/v100/compare_lines.py`](../../bench/v100/compare_lines.py) 采集：

```bash
python3 bench/v100/compare_lines.py \
  --image ninfer:v100-gemma4 --image ninfer:v1.5.0 \
  --model /workspace/models/swift-1.5-qwen3.8-27b-orcarouter-dflash2-nvfp4.ninfer \
  --extra-args "--spec mtp --draft-tokens 4 --lm-head-draft" --runs 2 --warmup 1
```

达标线：上游 sm70 线的 decode 从 ~14.8 tok/s 提升到 **≥50 tok/s**（fork 为 62.1 tok/s）；
若只有小幅提升，说明瓶颈不在注意力，应先用 `ninfer_bench` 拆解 decode round 的算子耗时再决定下一步
（fork 的 `docs/V100-PERF-PLAN.md` 里有现成的拆解方法）。

## 5. 风险

| 风险 | 说明 | 处置 |
|---|---|---|
| v2 与 fork 独有的 KV 布局/route 结构耦合 | 最可能的阻塞点 | 退化为"只移植算法"（§3 末尾） |
| 上游同一位置的 sm_70 路线与 v2 目标重叠 | 上游 `small_t_sm70.cuh` 也是 Volta 内核 | 先量化上游路线的耗时，再决定是替换还是新增 route |
| 与后续上游 merge 冲突 | `small_t.cu` 是双方都在改的热点文件 | 改动尽量集中、加显式注释标记本仓库意图 |
| 性能提升不达预期 | 4.3× 的差距未必只来自注意力 | 用算子级拆解定位（`docs/V100-PERF-PLAN.md` 的方法） |
