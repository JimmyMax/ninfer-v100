## 1. Oracle：上游自带的注意力单测

测试以 `ninfer_tests` bundle 形式打包（`tests/cmake/NinferTests.cmake`），需先编整个 bundle：

```bash
docker exec ninfer-sm70-build bash -c 'cd /build && ninja -j 16 ninfer_tests'   # 244 个目标，约 40 分钟
docker exec ninfer-sm70-build bash -c 'cd /build && ctest -R "^ninfer_softmax_attention_test$" --output-on-failure'
```

| 运行 | 结果 | 耗时 |
|---|---|---|
| `NINFER_SM70_ATTN_V2=1`（fork 的 v2 内核） | **Passed** | 271.2 s |
| `NINFER_SM70_ATTN_V2=0`（上游内核，对照） | **Passed** | 287.3 s |

该测试（`tests/ops/softmax_attention/causal_cache.cpp`，4383 行）逐存储类型对着**参考实现**比对，
覆盖到 `KvCacheStorage::Int8Group64`——正是 v2 接管的那条路径，容差如 `int8-g64 2.990e-3`。
**结论：v2 的移植在数值上是正确的**，此前的"贪心逐 token 一致"标准应作废
（不同归约顺序 + fp16 PV 累加链本来就会翻动个别贪心决策）。

## 2. 长上下文 A/B（Swift Qwen3.8-27B nvfp4，int8 KV，MTP 4 drafts，prefill-chunk 2048）

同一镜像、同一参数，只切 `NINFER_SM70_ATTN_V2`；`temperature=0`，输出上限 64 token：

| 上下文（服务端计数） | 内核 | prefill | decode | TTFT | 接受率 |
|---|---|---:|---:|---:|---:|
| 42,518 tok | `V2=0` 上游 | 361.1 tok/s | 16.7 tok/s | 1m 57.9s | 49.4% |
| 42,518 tok | `V2=1` fork v2 | 360.5 tok/s | **17.2 tok/s（+3.0%）** | 1m 58.1s | 49.4% |
| 152,711 tok | `V2=0` 上游 | 269.2 tok/s | 16.2 tok/s | 9m 27.7s | 51.2% |
| 152,711 tok | `V2=1` fork v2 | 268.9 tok/s | **17.1 tok/s（+5.6%）** | 9m 28.5s | 51.2% |

**没有复现 fork 记录的 +37%~47%（那是 186K 上下文下他们自己的模型与内核组合）。**

## 3. 由此得到的定量结论（本轮最重要的收获）

1. **decode 几乎不随上下文变化**：42K 时 16.7 tok/s → 152K 时 16.2 tok/s。
   如果注意力主导解码成本，这个曲线早该明显下滑。所以注意力（含 v2）在这条线上不是瓶颈。
2. **反推有效带宽可以定位真正的瓶颈**：Swift 模型 22.78 GB 权重。
   * 上游线 16 tok/s → 约 **365 GB/s** 有效权重带宽（V100-PCIE-32GB 峰值约 900 GB/s）。
   * fork 62 tok/s → 约 **1.4 TB/s**，**超过 V100 峰值**——说明 fork 并不是"每 token 把全部权重读一遍"
     的那条路径。
3. **原因是格式路线**：该 artifact 是 NVFP4。上游的 V100 路径**没有 NVFP4 W4A4**
   （`docs/build-linux.md` 明说：FP8 A8 与 NVFP4 W4A4 在 `sm_86`/`sm_70` 都不可用，
   那些权重走 **A16 路线**：先把 NVFP4 反量化成 FP16 再乘）。反量化的额外读写正好是
   数倍带宽，于是 16 vs 62 tok/s ≈ 4.3×。
4. **反过来印证 Gemma 4 为什么能跑 157 tok/s**：Gemma 的权重是 GGUF block 格式
   （Q4_K/Q5_0/Q6_K/Q8_0），上游 V100 **有原生 DP4A GGUF 内核**，不需要 A16 反量化。
   格式原生 → 带宽利用率高。
5. 因此：
   * **Qwen 在这条线上的杠杆在投影层**（NVFP4/FP8 的 Volta 原生路径，即 fork 的 QPN
     prepack + `nvfp4_volta_qpn_gemm` 那一套），不在注意力。
   * **Gemma 4 的杠杆在 MoE 专家与 GGUF 投影的 Volta 调优**（S3/S4），也不在注意力；
     照搬 v2 到 Gemma 没有意义（Gemma 还有自己的注意力实现，本开关对它无效）。
6. v2 本身**保留**：+3~6%、已通过 oracle、默认开启、零回归风险；但不要指望它解决 4.3× 的差距。
