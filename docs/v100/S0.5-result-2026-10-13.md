## A/B 实测（V100-32GB，Swift Qwen3.8-27B nvfp4，200K ctx，int8 KV，MTP 4 drafts，prefill-chunk 2048）

同一镜像、同一参数，仅切换 `NINFER_SM70_ATTN_V2`；预热 1 次后测 2 次，取末次：

| `NINFER_SM70_ATTN_V2` | decode | prefill | TTFT | 接受率 |
|---|---:|---:|---:|---:|
| `0`（上游 Volta 内核） | 15.1 tok/s | 19.3 tok/s¹ | 310 ms | 36.2% |
| `1`（fork 的 v2 内核） | **15.9 tok/s（+5.3%）** | 19.4 tok/s¹ | 295 ms | 39.6% |

¹ 这里的 prefill 数值是"响应重放"路径下的读数，不代表真实 prefill 带宽，仅作同等条件对照。

**输出一致性**：`temperature=0` 下两次运行的 `reasoning_content` 在**第 272 个字符**出现分歧
（2377 vs 2378 字符）。这不是"逐 token 一致"，符合预期——v2 改变了 QK^T 的归约顺序并启用
fp16 PV 累加链，浮点舍入不同会翻动贪心决策。**但这意味着 §4 的"逐 token 一致"验收标准必须改成
perplexity/oracle 验收**，否则无法区分"数值差异"与"真的算错"。

## 判断

1. **移植本身是成功的**：能编译、能跑、不崩、数值合理、短上下文有小幅收益。
2. **但它不是那 4.3× 差距的来源**。fork 自己记录 v2 的收益是
   "186K–193K 时 +37%~+47%，8K–32K 时 +4%~+17%"——即 v2 只在**长上下文**显著；
   本次测量是短上下文（76 token 提示），注意力在总耗时里占比很小，+5% 属合理量级。
   要复现 fork 的数字，必须在 32K/128K/186K 上下文下测。
3. **计划里的隐性假设被证伪了一半**：fork 在 Qwen 上快 4.3×，不能只靠注意力解释。
   按 fork 自己的 `docs/V100-PERF-PLAN.md`，它的加速面是
   **投影（QPN prepack + Volta GEMM）→ MoE → 注意力** 三层，83 个 Volta 文件 / 11.5k 行。
   注意力只是其中一层。
4. **对 Gemma 4 的直接意义**：Gemma 的 V100 加速应同时覆盖
   GGUF 投影（S3）与 MoE 专家（S4），而不是只做注意力（S2）。

## 下一步的正确顺序（需要决策，见 PLAN 的 S0.5 门禁）

1. **先补验收手段**（半天）：构建上游自带的 FP64 oracle 测试或 `ninfer-perplexity`，
   把"数值差异 vs 真错误"分开。没有这个，后面每一步加速都无法安全推进。
2. **再做长上下文 A/B**（半天）：32K / 128K 两档，验证 v2 是否复现 fork 的 +17%~+47%。
   128K prefill 在 V100 上约 10–20 分钟/次，需要预留时间。
3. **然后选下一层**：
   * 若目标是 **Gemma 4 提速** → 直接进 S3（GGUF 投影）+ S4（MoE 专家），S2 顺带做
     （Gemma 的滑窗/全局注意力需按自己的几何重写，v2 只是技术参照）。
   * 若目标是 **追平 fork 的 Qwen 性能** → 需要移植 QPN prepack + Volta GEMM 那 8 个
     `linear/nvfp4`、7 个 `linear/fp8`、6 个 `linear_swiglu/*` 文件，量级远大于本次。
