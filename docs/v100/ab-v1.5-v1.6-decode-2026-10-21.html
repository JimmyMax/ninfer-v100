NInfer V100:v1.5 vs v1.6 全面对比

2026-10-21 · Tesla V100-PCIE-32GB(sm_70,CUDA 12.8)· 同一张卡、同一模型文件、同参数 A/B · v1.5 = ninfer:v1.5.0 · v1.6 = ninfer:1.6.2(含长上下文 prefill 崩溃修复 ab6f496)
一句话结论:同模型(两版本都支持的 Swift v2 制品)下,v1.6 的 MTP 解码并不慢,反而快 3%~12%; 纯解码在 ≤27K 持平,82K 时慢 6%。真正的回退是 82K 长上下文 prefill 慢 10%(v1.6 flash 路线在高键数下 不如 v1.5 的 prompt 路线)。「1.6 比 1.5 慢」的体感更可能来自换了模型:你的生产模型 Coder390 在 v1.5 上根本无法加载(制品未注册),它自身的 MTP 接受率(28~35%)低于之前 OrcaRouter/Swift 线 (39~50%),等效解码速度自然更低。

5. 「1.6 decode 慢」的可能来源,按可信度排序

  • 模型换了(最大)。当前 Coder390 的 MTP 接受率 28~35%,比旧 OrcaRouter 线的 39~50% 低,等效解码 ~10 tok/s 更低。且 Coder390 在 v1.5 上不可加载,你手上没有「Coder390 on v1.5」的基线,对比只能是跨模型的记忆对比。
  • 82K 未命中缓存请求的 TTFT。v1.6 flash 路线在高键数下比 v1.5 prompt 路线慢 10.8%(697 vs 781 tok/s),82K 冷请求 TTFT ~13 s 差距。你日常多数请求命中前缀缓存,所以这不是每请求感受,但新话题/冷会话会明显。
  • 双 lane 第二请求的编排。v1.6 第 1 轮里第二请求总完成晚 ~4 s(见 §2),并发高峰下的主观感受。
  • 解码本身不是。同模型 MTP 解码 +3~+12%,纯解码 ≤27K 持平、82K −6%(单点小量)。

6. 测法与限制

  • 硬件:Tesla V100-PCIE-32GB(sm_70 构建,CUDA 12.8),单卡独占;每次测试前 docker rm -f 清理,测完恢复生产容器。
  • 提示:合成中文长文(逐条编号 filler),7.6K / 27K / 82K 三个长度;82K 提示以 27K 提示为真前缀(故 §1 的 82K TTFT 两版本缓存状态不同,已在表内标注)。
  • 贪心(temperature 0),输出 192 token(双 lane 96);每个 (版本, 模式, 长度) 单点,未重复。1.6 两个 82K 点的相互偏差 <1%,量级可信;单点 ±3% 内的差异按噪声处理。
  • v1.5 无 --ngram-draft-tokens 旗标(该特性 v1.6 才引入);MTP 组语义对齐(均为纯 MTP,无 n-gram 混合草稿)。
  • 两镜像均读同一模型文件;v1.6 = ninfer:1.6.2(含 ab6f496 崩溃修复,二进制 sha256 0f3ea6f3…aa867cc)。

7. 建议的后续(未做)

  • 82K prefill 回退:对 v1.6 flash 路线 vs v1.5 prompt 路线做 kernel 级剖析,找交叉键数, 按可见键数选择路线(如 keys > ~70K 退回 prompt 路线)可收回 ~10%。
  • 纯解码 82K −6%:量级小,若做上述路线调整可一并复核。
  • 双 lane 编排:第 1 轮第二请求晚完成 ~4 s 的成因(成批条件),可选优化。
