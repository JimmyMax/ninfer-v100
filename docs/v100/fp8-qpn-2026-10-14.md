# FP8 投影走 Volta QPN + 加载时 prepack（2026-10-14）

> 承接 [`profiling-nvfp4-2026-10-13.md`](profiling-nvfp4-2026-10-13.md)。NVFP4 那条做完（decode
> 15.9 → 31.4 tok/s）之后，账本里剩下的最大单项就是 **fp8**：Swift 这个 artifact 里 fp8 有 130 个
> 张量 / 9.76 GiB，而且其中 64×2 个是每层的注意力输入投影与输出投影，正好落在 decode 的关键路径上。
> 本文件记录把 fork 的 FP8 QPN + CUTLASS 路径正向搬到上游 sm_70 线的结果。

## 1. 改动结构

fork 的 fp8 路线是"**QPN 拥有受支持形状的全部宽度**"（宽 T 按 32 列分块），与上游 sm_70 的
"≤8 列才走 NInfer 向量核，>8 列反量化到 FP16 走 cuBLAS"完全不同。按这个结构搬：

| 位置 | 形状（n×k） | t ≤ 32 | t > 32 |
|---|---|---|---|
| 普通 `linear`（o_proj、output_head） | 5120×6144 / 248320×5120 | QPN（32 列分块） | CUTLASS（≥33，按权重上限回退 QPN） |
| `attn_input_proj`（每层 14336×5120） | 14336×5120 | QPN | CUTLASS |
| `linear_add`（fp8 残差） | 5120×17408 | QPN 残差 | CUTLASS + `residual_add` |
| `gdn_input_proj` | 16384×5120 | QPN | CUTLASS |
| `linear_swiglu` | 34816×5120 | QPN **split**（FP32 平面） | **回到上游阶梯** |

`linear_swiglu` 的宽 T 是特意交还给上游的：它的 A16 契约要求激活以 FP32 穿过 SwiGLU，单个
CUTLASS 的 BF16 gate_up 平面差 0.23%，判为不等价（见 §4）。

### 1.1 两个契约坑（决定了实现形状）

1. **容量必须"恰好等于"峰值。** 上游对 workspace 的验收是
   `workspace.peak_used() == capacity(T,T)`（每个宽度精确相等），而且**便利调用形式（不带 arena）在
   decode 宽度必须看到容量 0**。fork 的 FP16 staging 把激活先搬进暂存区，会让 QPN 需要 workspace
   → 直接把这条契约打破。因此这里的 QPN 是**直读 BF16 激活、零 workspace**。
   相应地，容量函数**绕开 route table**：V100 的 `device_profiles.json` 对
   `unified/fp8_*` 声明了 unified 分段，容量加法不能去查表（NVFP4 阶段的同款教训）。
2. **hook 必须在 route 查表之前，并且只截 A16 政策族。** 否则上游 FP8 的 A8/A4 路线会被抢走，
   而它们的激活量化契约与这里不同。现在 hook 条件是
   `!allows_a8(policy) && !allows_a4(policy)`，A8/A4 在 sm70 上干净地 SKIP（"requires an
   sm_100a or sm_120a GPU"）。

单点排除优于逐个 wrapper 改：`sm70_project.cu` 的 `covered_format(fp8, k)` 对 QPN 形状返回 false，
所有 wrapper 的 `sm70::covers()` 自动失效（NVFP4 阶段同款手法）。

## 2. 加载时 prepack

`src/artifact/permute_fp8_qpn.cu` 在上游的 materializer 里、每次上传之后**就地**把 code 平面重排成
QPN8 的 fragment 序（`[N/32 tile][K/128 block][8 slices][lane32]`），所以挂起/恢复后会重新施行，
且权重保持注册时的字节数不变。scale 平面不动：QPN8 每个输出行读一个 BF16 scale，而行不移动。

* 触发条件：`FP8_E4M3FN_ROW_BF16` + `RowScale` + `n%32==0` + `k%128==0` + `k/128 ≥ 8`。
  `fp8_prepack_sm70.cu` 退化为薄包装。
* 三个必须记住的点：
  * `QuantLayout::VoltaQpnPrepacked` 与 NVFP4 **共用**，所以布局辅助函数现在按
    `(format, layout)` 取键：`weight_view.cpp` 必须为 prepacked 的 **FP8** 父对象也填上行 scale 元数据，
    否则 Weight 到手时 `scale_ne`/`scale_nb` 全空，消费者一律以 "invalid FP8 weight" 拒绝。
    症状是启动即失败（`fp8 linear_add: invalid FP8 weight`），而 instrumented 打印落在 nvfp4 分支里
    完全看不到 —— 排查时别再把探针插进 `is_block_scale_nvfp4` 分支。
  * **1.27 GB 的 output_head 不能走宽 T CUTLASS**：反量化出的 FP16 副本 2.54 GB，而引擎按"计划过
    的最大宽度"预留，直接把运行时预留推过剩余显存。现在的规则是
    `kFp8CutlassWeightLimitBytes = 256 MiB`：FP16 副本会超过它的形状留在分块 QPN（零 workspace）；
    生产 prefill 里这个头也只算最后几列。
  * 两个形状**故意**不进 prepack 名单：GDN 输入投影（16384×5120，本模型里消费方是融合的
    `fp8_gdn_input_proj_conv_record`）与 fp8 SwiGLU gate_up（34816×5120）。两者都按行主序读，
    并且面对 prepacked 权重会**显式拒绝**而不是算错。

## 3. 验收

### 3.1 算子级（`ninfer_linear_bench --prepack`，冷缓存，T=1）

| 形状 | 行主序 | prepacked | 带宽 |
|---|---:|---:|---:|
| 17408×5120 | 184.3 µs | **144.4 µs** | 484 → 618 GB/s（DRAM 53.9 → 68.8%） |
| 5120×6144 | 69.6 µs | **61.4 µs** | 452 → 513 GB/s |

### 3.2 等价性

* 新 oracle `ninfer_linear_fp8_qpn_prepack_test`：`ops::linear` / `ops::attn_input_proj` /
  `ops::linear_add`，T = 1, 5, 17, 32, 33, 129，native 与 prepacked **位精确**（QPN 与 CUTLASS 两条路都测）。
* `fp8|nvfp4|attn_input_proj|gdn_input_proj` 全量扫测 **43/43 通过**（含 legacy/unified 变体）。
  其中 2 个 `ninfer_linear_fp8_a16_*_routes_test` 首轮是 cudaMalloc OOM（生产容器占 23.5 GB），
  停生产复跑即通过 —— 是显存竞争，不是代码。

### 3.3 端到端（同 prompt、贪心、MTP4，接受数完全一致）

| 臂 | 短 decode | 短 prefill / TTFT | 42K decode | 42K prefill | 42K TTFT |
|---|---:|---:|---:|---:|---:|
| A 会话起点（`v100-gemma4`） | 14.4 | 82.0 / 774 ms | 15.9 | 345.7 | 47.4 s |
| B 仅 NVFP4 阶段 | 31.0 | 123.0 / 559 ms | 32.9 | 407.8 | 40.2 s |
| **C 再加 fp8 阶段（`v100-fp8`）** | **31.1** | **144.3 / 501 ms** | **32.9** | **951.2** | **17.4 s** |

三阶段合起来：decode **14.4 → 31.1**（42K：15.9 → 32.9，2.07×）、42K prefill **345.7 → 951.2**
（2.75×）、42K TTFT **47.4 s → 17.4 s**。

* 42K 输出与基线**逐字相同**；MTP 接受数三臂一致（51/144、39/96）。
* 短输出在第 85 字符处分叉：基线"这种关联**并不传递普通信息，却体现了**量子力学中非经典的空间关联
  特性"，本方"这种关联**不能用来超光速传递信息，但它是**量子力学中真实且已被实验验证的现象" ——
  语义等价、措辞不同。原因是张量核的累加次序变了（fp16 张量核 vs sm70 SIMT），在一个近似并列的贪心
  token 上翻了一次。判为可接受，记录在此以便日后对照。

## 4. 遗留

* `linear_swiglu` 的 t>32 仍在上游阶梯（fp32 反量化 + cuBLAS + `silu_mul`）。要再压这一段，需要一条
  "BF16 gate_up 平面 + FP32 激活"的 CUTLASS epilogue，而不是单个平面。
* 分块 QPN 的宽 T 在真实 prefill 下每次读整份权重（o_proj 5120×6144，t=2048 → 64 块）。本阶段实测
  42K prefill 951 tok/s 已经够用，未动；若后续成为瓶颈，改走 CUTLASS（受 256 MiB 上限约束）。
* 注意力线（S2）与它无关，见 [`PLAN.md`](PLAN.md)。
