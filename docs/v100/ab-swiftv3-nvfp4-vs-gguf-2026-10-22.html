0. 对比前提

  • 两个工件是同一 Swift-1.5 v3 权重的两种量化:NVFP4(swift-1.5-...-nvfp4-v3.ninfer,设备权重 18.4 GiB)与 llama.cpp 标准导出 Swift-1.5-Qwen3.8-27B-Q4_K_M.gguf 转换件(16.23 GiB:Q4_K 10.66 / Q6_K 3.84 / Q8_0 1.30 / 其余 0.65 GiB)。
  • 同一引擎 ninfer:1.6.2-ggufopt(1.6.1 基线 + GGUF vec T≥2 的 L1I 修复),隔离变量只剩量化表示。
  • 两边都有 MTP(nextn)头,greedy,96 输出,无 ngram,无 DFlash2 drafter;int8 KV;1 lane。 提示词为固定重复 filler(7,518 / 27,250 / 89,326 tok)。
  • 本报告同时覆盖用户要求的「最快 prefill/decode 配置」调参矩阵(prefill chunk 1024/2048/4096、MTP d2/d4/d6/d8、 --max-concurrency 2、--ngram-draft-tokens 15),以及短 prompt(~1K)对比与1.5.0 基线。
本发布测得的最快配置(V100-32GB,greedy,96 输出,int8 KV): ninfer-serve model.ninfer --max-context 200000 --prefill-chunk 2048 --kv-capacity auto --kv-dtype int8 --max-concurrency 1 --spec mtp --draft-tokens 4 --lm-head-draft —— NVFP4 工件:短 prompt(982 tok)MTP decode 84.7 tok/s(58.9% 接受率,1.7.0 测得的最高吞吐)、 27.3K MTP 75.5 tok/s(52.0%)、27.3K plain 32.7、27.3K prefill 1,006 tok/s;GGUF 工件同 decode 参数 + --prefill-chunk 4096(27.3K prefill 988、MTP 73.8)。

3. 调优后 A/B 结论

  • 纯 decode:两边打平(±3%)——GGUF 少 2.2 GiB 权重却只差 2–3%(27K 31.8 vs 32.7),Q4_K 系列 vec 内核已接近其带宽上限。
  • MTP decode:NVFP4 领先 2.3%(27K 各自最优 chunk)~5.0%(82K ch2048)——每步验证速率差(GEMV 每字节效率),接受率两边在漂移带内。
  • Prefill:GGUF 用 4096 chunk 后 82K 追平 NVFP4,27K/7.6K 差 2%。
  • 对「GGUF 侧还能否更快」:有,但有限。见 §4 的 profiling 分解。

3.3 缺口分解(27K plain:32.0 tok/s,31.25 ms/tok;带宽上限 21.8 GB/tok ÷ 803 → 36.9 tok/s)

  • 多 stream 争用(Q4_K ~6 ms/tok,~19%):并发下 484 GB/s vs 隔离 644 GB/s。decode 图 965 launch/token,vec 大核与 rmsnorm/quantize/GDN/attention 小核跨 stream 共享 SM。修复 = GEMV+后处理融合或调度重构,周级工程。
  • Q6_K 内核低效(~2–3 ms/tok,~7–9%):op 级仅 54–63%。根因:210 B 行只有 2 B 对齐,每 32 元素 slice 要 16 次 2 B 加载,LSU 指令翻倍且无法向量化。修复需转换端重打包布局(16 B 对齐,+22% Q6_K 流量,预计净收益 ~2–3%)。
  • attention/KV(~5 ms/tok,27K):int8 KV 读 3.6 GB/tok,已近带宽;82K 时占比升至 ~20%,无生产选项可再降。
  • 小核(rmsnorm/quantize/gdn/conv ~2–3 ms/tok):各已很小。

3.4 结论:GGUF 侧还有空间,但不大且不便宜

  • 现实可兑现的剩余空间 ~3–6%(小核 + 边角);大空间项(Q6_K 重打包 ~2–3%、Q4_K 争用融合)是周级工程。
  • 与 NVFP4 的差距(MTP 2.3–5.0%)本质是量化表示本身:NVFP4 的 4-bit 值 + E4M3 标量解码每元素整数 ALU 更少、行 16 B 对齐;即使做完 GGUF 侧全部优化,decode 也只是接近而非超过 NVFP4。
  • 已排除项:T=1 已全展开;T≥2 已 #pragma unroll 1(L1I 修复,收益 +18.9% e2e);kRows/TC 路线在小 T 已测量拒绝。

5. 测法与限制

  • 每 case 全新容器(冷 KV/上下文);请求后从响应 timings(引擎自报)取 prefill/decode/接受数;与 serve 日志 req#N done 行交叉核对一致。
  • greedy;输出 96 tok;接受率 = draft 接受数/草稿数(仅神经草稿,无 ngram)。
  • 接受率跨提示词/分块漂移 ±5pp;单点 decode 速率重复测量波动 ±2%。
  • ECC on(V100 出厂状态):带宽 803 GB/s(关 ECC 可 ~902)——两侧同等受影响。
  • §1 的版本 A/B(1.7.0 vs 1.5.0)在同一会话内背靠背运行(每 case 全新容器,同一 GPU 状态); 短 prompt 982 tok、27.2K prompt 27,222 tok 的 filler 与 §2 矩阵(27,250)略有差异,接受率数字不可跨 prompt 直接对比。 原始日志:v17_ab_runs.txt。
