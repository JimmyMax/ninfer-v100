# V100-32GB 基线数据（2026-10-12）

本文件记录本仓库 `gemma` 分支在 **Tesla V100-PCIE-32GB** 上的第一条可用基线，
作为后续所有加速阶段的对照。**所有数字必须用同一脚本、同一 prompt、预热后测量**
（见 §4），否则冷启动会把结论带偏。

## 1. 环境

| 项 | 值 |
|---|---|
| 宿主机 GPU | `GPU 1 = Tesla V100-PCIE-32GB`（32,768 MiB，ECC 开启 → 可用约 30.7 GiB）<br>`GPU 0 = RTX 4080 SUPER`（本方案不使用，`sm_70` 二进制跑不了） |
| 驱动 / CUDA | 580.159.03 / CUDA 13.0（驱动）；构建用 CUDA **12.8**（CUDA 13 不支持 `sm_70`） |
| 引擎 | `iamwavecut/ninfer-all` `master` = `fcc4928a`（含 PR #58 的 sm_70 移植） |
| 镜像 | `ninfer:v100-gemma4`（`ninfer-serve 0.12.0-rtx3090+unknown`，416 MB 二进制，CUDA 12.8 `sm_70`） |
| 运行时基底 | `ninfer:v100-stable`（CUDA 12.8 runtime + ffmpeg 6.1 + libcurl） |
| 模型目录 | `/mnt/data/dockerdata/llama-cpp/models` → 容器内 `/workspace/models`（只读） |

## 2. Gemma 4 26B-A4B（本分支）

Artifact：`Gemma4-26B-A4B-QAT-Uncensored-HauhauCS-Balanced-MTP-ninfer-v3.ninfer`
（18,194,661,888 B；Q4_K 133 + Q8_0 28 + Q5_0 32 + Q4_0 19 + Q6_K 14 + BF16 111 + FP32 580 张量）

启动参数：

```
ninfer-serve /workspace/models/Gemma4-...-ninfer-v3.ninfer \
  --host 0.0.0.0 --port 8000 --api-key sk-itzy --model-id qwen \
  --max-context 200000 --prefill-chunk 2048 --kv-capacity auto --kv-dtype int8 \
  --max-concurrency 2 --spec mtp --draft-tokens 2 --preserve-thinking --vision
```

启动日志要点：

| 指标 | `--draft-tokens 2` | `--draft-tokens 4` |
|---|---:|---:|
| decode | **157.5 tok/s** | 119.0 tok/s |

| TTFT | 82 ms | 81 ms |

功能验证：

* 文本对话 ✓
* **vision**（96×96 测试图，红/蓝/黄 + 三角形/X 形）→ 正确描述，285 prompt token ✓
* `--max-context 200000` + `--kv-dtype int8` ✓（KV 池 3,338 MiB，启动后剩 8.82 GiB）
* 经 Nginx 域名 `llama.x.jimy.top` 访问 ✓（自签证书，CLI 需 `-k`）
* `ai-net` 内部 `llama-cpp-text:8000` ✓（Hermes 可达）

参考：上游自己的 16GB 卡数据（`docs/performance/tesla-v100-2026-10.md`）为
短对话 164.3 tok/s（无投机）/ 226.3 tok/s（MTP 2 drafts）；本机 32GB 目前 157.5 tok/s，
即 **S1 的调优空间目标**。

## 3. 两线 A/B（同一 Qwen artifact）

Artifact：`swift-1.5-qwen3.8-27b-orcarouter-dflash2-nvfp4.ninfer`（22.78 GB），
同一组参数（`--max-context 200000 --kv-capacity auto --kv-dtype int8 --max-concurrency 2
--spec mtp --draft-tokens 4 --lm-head-draft --preserve-thinking --vision`），预热 1 次后测 2 次：

| 实现 | decode | prefill | TTFT | MTP 接受率 |
|---|---:|---:|---:|---:|
| 上游 sm70 线（本分支，`ninfer:v100-gemma4`） | **14.2 / 14.8 tok/s** | 81.6 tok/s | 975 ms | 32.4 / 34.9% |
| fork（`ninfer:v1.5.0`，`JimmyMax/ninfer-v100`） | **62.1 / 62.1 tok/s** | 191.5 tok/s | 510 ms | 32.8% |

差距 **≈4.3×**，来源是 fork 的 Volta 特化内核与 route 表（`fp8_attn_input_volta_qpn.cu`、
`nvfp4_volta_qpn_gemm.cuh`、`small_t_i8` v2、`prompt_volta.cuh`、`volta_mma.cuh`）。
这是 **S0.5** 要验证"能否正向搬运"的样板。

> 注意：未预热的首请求在本机可低至稳态的 1/4（例如同一次实验预热前为 15.9 vs 60.1 tok/s），
> 因此不要把首请求数字当作基线。

## 4. 复现方式

```bash
python3 bench/v100/compare_lines.py \
  --image ninfer:v100-gemma4 --image ninfer:v1.5.0 \
  --model /workspace/models/swift-1.5-qwen3.8-27b-orcarouter-dflash2-nvfp4.ninfer \
  --extra-args "--spec mtp --draft-tokens 4 --lm-head-draft" \
  --runs 2 --warmup 1
```

脚本会：启容器（`--gpus '"device=1"'`）→ 等 `listening on` → 预热 → 连测 N 次 →
打印 markdown 表格（decode / prefill / TTFT / 接受率），并附启动时的 `capacity` 行。

## 5. 已知限制

* fork 的 `--lm-head-draft` 对 Gemma 4 无效（assistant 没有 proposal head），带上会在启动时报
  `Gemma 4's assistant has no --draft-min-p, n-gram archive, --mtp-attention-window or proposal head`。
* 上游 sm70 路径在 V100 上**没有** FP8 A8 与 NVFP4 W4A4（与 `sm_86` 相同），相关权重走 A16 路线。
* Gemma 4 的全局注意力层只缓存 V（K 由 V 与 `k_norm` 派生），所以该平面的 KV 字节数按 V 计。
* 视觉塔驻留显存时约 1.07 GiB；`--vision-residency overlay` 可降到约 0.14 GiB。
