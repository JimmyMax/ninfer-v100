# 1.6 与 1.5 的性能差距:归因与收敛计划(2026-10-20)

来源:[JimmyMax/ninfer-v100#2](https://github.com/JimmyMax/ninfer-v100/issues/2) 中 Jellypowered
的实测报告(2026-10-18):同一制品 `qwen3_8_27b_nvfp4.ninfer`、同一组参数,只更换构建目录,1.5 线
(`archive/fork-master`)MTP 接受率平均 **75%**,1.6 线 **60–68%(随任务变化)**,而 1.6 的 prefill 与
tok/s 反而**快约 10%**;报告者据此判为"intelligence regression",暂留 1.5。

本文把报告拆成三个可独立验证的原因,并给出按收益/风险排序的收敛计划。

## 0. 基线(以远程 `main` 为准)

本仓库的工作树在 2026-10-20 重建到 `origin/main` 上(此前是一个 gitdir 已失效的外部 worktree)。
核实过的三件事:

- `origin/main`(v1.6.1,tip `12a74bd`,2026-10-19)**是上游 `fcc4928a` 的后代**,`fcc4928a`
  (2026-10-12,上游 PR #58 的 merge)之后 **main 没有再 merge 过上游**;`git merge-base
  origin/main upstream/master` 正是 `fcc4928a`。
- 重建前后的树**逐字节一致**,即本文之前把"我们的树"当分析对象是对的,它就是 v1.6.1。
- 相对上游 master,`main` **落后 148 个提交**,其中 **39 个**触及 V100 关键路径
  (`src/ops/linear/sm70`、`dense/causal_cache`、`src/models/qwen3_5`)。

因此:**1.6.1 发布版本身缺这些修复**,不是某个本地分支缺;下面第 3 节的清单既是对 1.6 的差评,
也是收敛的入口。

## 1. 结论

| 编号 | 原因 | 状态 | 证据 |
|---|---|---|---|
| R1 | **度量口径**:1.6 只要带 `--spec` 就默认 `--ngram-draft-tokens 15`,拷贝轮把列数灌进 MTP 的接受率分母;1.5 线没有 ngram 代码,是纯神经 MTP | 已修(`f0ee4fe`、`edcb69d`) | `src/product/speculative_options.h`(旧)、`decode.cpp:868`、`operational_log.cpp:298`;`archive/fork-master` 文件树 0 个 ngram 文件 |
| R2 | **草稿/验证链的真实差距**:同配置纯 MTP 下 27K 上 54.3% vs 58.0% | 待修 | 本目录 `PLAN.md` S0.14 |
| R3 | **验证端 KV 切分不规范**(最可能的 R2 成因):masked 验证行按"最后一个 live 位置"而不是 tile 窗口切 key,split-KV 归约顺序因此随 drafts 变化,近 tie 的 argmax 会翻转 → 正确草稿被拒 | 待移植上游 `ddacb96` | 上游提交说明 + 其新增的 bit-identical Op 用例 |
| R4 | **sm_70 把超出 FP16 范围的 BF16 值饱和**(>±65504),投影/注意力结果失真 | 待移植上游 `2d69547`(依赖 `67778be`) | 上游提交说明:V100 上 120 个 Q8_A16_wide_range 与 9 个 BF16 attention 用例失败 |

R1 解释了报告里**大部分**落差(算术见下);R2 是 1.5 与 1.6 之间真实存在、可被 R3/R4 解释的部分。

## 2. R1 为什么会让 75% 显示成 60–68%

1. `--spec` 开着时,宽度默认 15(`kDefaultNgramDraftTokens`)。
2. 任意一条 lane 命中拷贝,整轮就是 copy round:`verify_window` 从 `draft_window`(4)变成 15,
   走 `ngram_graphs`,自适应控制器整轮跳过(`decode.cpp:721-734`)。
3. 拷贝行的 extent 是**拷贝长度(≤15)**,神经行才是 `mtp_draft_count`(4)(`decode.cpp:763-768`)。
4. 两者此前计入**同一个** `drafted_tokens`/`accepted_tokens`(`decode.cpp:868`),
   日志百分比 = `accepted / drafted`(`operational_log.cpp:531`)。

纯神经 4 取 3 = 75%;拷贝轮 10 取 6 = 60%。拷贝轮占到 30–50% 时,合并值就是 60–68%,
且随任务里"可复制文本"的比例波动——与报告"depending on task"一致。输出质量不受影响
(每个 token 仍由目标模型验证;`PLAN.md` S0.12 用逐字相同的贪心输出验证过)。

已实施:
- `f0ee4fe`:拷贝草稿改为**显式启用**(默认 0),移除 `apply_default_ngram_draft_tokens` 与三处
  `width_explicit` 管道,同步 CLI/bench 帮助、`docs/cli.md`、`docs/ngram.md`、`docs/serving.md`。
- `edcb69d`:`speculative.*` 只统计**神经**行,拷贝轮只进 `ngram_*`;copy round 中携带神经草稿的行
  仍照常计入。此后跨配置的接受率可直接比较。

`small_t_bf16.cuh` 里带出 `f98d88a`/sm75 的代码块)。

结论:**优先一次 merge,而不是串行 cherry-pick**;只有 merge 里无法调和的单点(如已在注释里
标明依赖缺失结构的块)才按第 3 节的规则裁剪。

## 4. 收敛计划

### 步骤 0(已完成)

- 工作树重建到 `origin/main`(真实历史、可 merge 上游、保留 `backup/imported-gemma`)。
- 修 R1 的度量口径与默认值(`f0ee4fe`、`edcb69d`)。

### 步骤 1:一次 merge 上游 `master`—— 把 R3/R2/R4 全部带进来

`git merge --no-ff upstream/master` 一次拿进 148 个提交(含 `ddacb96`、`6428248`/`c5f855b`/
`f98d88a`、`67778be`+`2d69547`、`a15f211`、`c30f94e`、`aef5f5af`、`3bc27f0`),按 12 个冲突逐项解决:

1. **FP8 三处 + `launch.h` + `small_t_i8_launch.cuh`**(S0.6/S0.17 钩子 vs 上游 unified 路由):
   同一形状若上游路由已覆盖则以**上游为准并删除我们的钩子**(避免双路径),否则保留钩子并把上游
   分支并入 sm_70 支路;两边的 sm_70 判定条件合并成一个入口。
2. **`prompt_sm70.cu` / `storage_trades.cpp`**: 取上游结构 + 保留本线的 sm_70 分支。
3. **CI / 文档 / `tests.cmake`**: 取上游文件 + 保留 V100 的构建与用例条目。

合并后先做回归,再谈性能: `ctest -R "causal_cache|small_t|gemma4|artifact|gdn"`,外加
`--spec mtp --draft-tokens K`(K=1..7)与 `--spec none` 在 4K/27K/128K 上的**逐 token 一致**。
上游 `ddacb96` 自带的 live-列逐位一致 Op 用例必须进 `tests/ops/tests.cmake`。

### 步骤 2:保住 1.6 已经赢的那部分

merge 会把上游对 prefill 路线的改动一起带进来,而本线在 S0.6/S0.17/S0.18/S0.20 上的收益依赖
自研钩子。合并后立刻重跑 27K A/B(v2 与 v3 制品、nvfp4 与 GSQ、Gemma 26B/31B),
门槛:prefill 不回退到 951 tok/s 以下、Gemma 31B decode 不低于 48.8,否则回退对应钩子。

### 步骤 3:验收 R3 是否真被修好

同制品同参数(纯 MTP、d4、int8 KV)重测 27K:纯神经接受率应从 54.3% 升到 ≥ 58%;若未达标,
再在草稿链一侧归因(MTP 草稿注意力窗口、state dtype、head 精度三条线,逐条 A/B)。

### 步骤 4:设备档位补齐

上游 `43e7fa8f`/`32a7c053` 的 36 个内置档位含 **V100-SXM2-32GB**,本树只有 16GB 档;
本机与报告者都是 32GB 卡,补齐后再标定 `attn_i8_small`/`t2_i8_small` 等档位。

## 5. 验收标准("1.6 超越 1.5")

同一制品、同一参数(`--spec mtp --draft-tokens 4 --lm-head-draft --ngram-draft-tokens 0`,
int8 KV)、同机同功耗上限,27K 请求:

| 指标 | 1.5 参考 | 目标 |
|---|---|---|
| 纯神经接受率 | 58.0% | ≥ 58%(并给出 4K/27K/128K 三个深度) |
| 27K decode | 81.7 tok/s | > 81.7 |
| 27K prefill | 1.00k tok/s | ≥ 1.00k(不得回退) |
| `--spec none` 一致性 | 逐 token 相同 | 保持,且扩到 K=1..7 |

同时报告:短上下文 decode(1K)、多请求 1/2/4/8、以及 16 GB V100 上的最大上下文不下降。

## 6. 风险

- 一次 merge 是**大行为变更**(148 个提交,含前端/服务/MoE 流式等与 V100 无关的部分),而这些
  改动本身已在上游的 3090/4090/5090 上验证过;本线的风险集中在上面 12 个文件里的 5 处 sm_70 钩子。
- 注意力内核的移植是"语义 + 结构"同时变,容易引入数值回归 → 先跑
  `ctest -R "causal_cache|small_t|gemma4"` + 逐位一致用例,再看 tok/s。
- `2d69547` 依赖 `67778be` 的宽投影分块; merge 会两条一起带到,不再需要单独判断。
- 我们这台的 V100-PCIE-32GB 与报告者的 SXM2 功耗上限不同(250 W vs 300 W),
  跨机比较必须同卡同功耗,结论以本机 A/B 为准。
