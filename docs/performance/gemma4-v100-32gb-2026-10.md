# Gemma 4 on a Tesla V100-32GB, October 2026

What the two Gemma 4 artifacts do on one **Tesla V100-PCIE-32GB** (sm_70, 250 W — its default power
limit, no cap applied), measured on that card with the sm_70 build of this branch, the same source
`ghcr.io/jimmymax/ninfer-v100:sm70` packages. Driver 580.159.03. ECC is on, as it is by default on
this card.

## How these were measured

- One request per row, greedy (`temperature 0`), the same **5,513-token prose prompt**, **500 output
  tokens**, `--kv-dtype int8 --prefill-chunk 2048 --ngram-draft-tokens 0`.
- Each row is a fresh server start, so the prompt is prefilled cold (no prefix cache hits).
- The figures are the server's own `req#1 done |` line: `prefill` and `decode` in tokens per second,
  `mtp accepted` as accepted drafts over proposed ones.

```bash
docker run --rm --gpus device=1 -p 8009:8009 --ulimit memlock=-1 \
  -v /path/to/models:/workspace/models:ro ghcr.io/jimmymax/ninfer-v100:sm70 \
  /workspace/models/Gemma4-31B-QAT-Uncensored-HauhauCS-Balanced-MTP-ninfer-v3.ninfer \
  --host 0.0.0.0 --port 8009 --model-id gemma31 --max-context 32768 --kv-dtype int8 \
  --prefill-chunk 2048 --spec mtp --draft-tokens 4 --ngram-draft-tokens 0
```

## The numbers

| model | artifact | weights | speculation | prefill | decode | MTP acceptance |
|---|---|---:|---|---:|---:|---:|
| Gemma 4 31B (dense, 60 layers, hidden 5376) | `Gemma4-31B-QAT-Uncensored-HauhauCS-Balanced-MTP-ninfer-v3` | 17.6 GiB | MTP, 4 drafts | 715 tok/s | **54.1 tok/s** | 342/628 (54.5%) |
| | | | MTP, 3 drafts | 714 | 52.8 | 65.4% (a 79-token answer) |
| | | | none | 720 | 27.4 | |
| Gemma 4 26B-A4B (128 experts, 8 per token) | `Gemma4-26B-A4B-QAT-Uncensored-HauhauCS-Balanced-MTP-ninfer-v3` | 16.9 GiB | MTP, 2 drafts | 2.39k | **157.2 tok/s** | 294/410 (71.7%) |
| | | | none | 2.39k | 120.3 | |

Both are GGUF-derived, so both run through the ggml bridge with per-tensor block dequantization.

Context on the same card: `--max-context 32768` with int8 KV leaves the 31B `runtime 3.32 GiB |
free 10.5 GiB`; the 26B reports `free 14.1 GiB` at 28,672 tokens. The 31B also runs 16K and beyond
without changing its rates — the prompt above is 5.5K, and the page's earlier 2K-prompt runs land
within 2% of it.

## What the numbers say

- **A dense model decodes at the speed its weights move.** The 31B reads all 17.6 GiB per token:
  27.4 tok/s is about 517 GB/s against the ~790 GB/s this card's HBM2 delivers with ECC on, which is
  what a block format with per-tensor dequantization reaches. Speculation is the lever that works
  here — verifying four drafts per weight read takes the same traffic to 54.1 tok/s, 2.0×.
- **An A4B reads a fraction of its file.** The 26B's artifact is 16.9 GiB, but a token touches the
  shared parts plus 8 of 128 experts, which is why it decodes at 120.3 tok/s unspeculated — 4.4× the
  dense model from a file 4% smaller. Speculation adds less on top (157.2, 1.3×) because the weight
  read is already a smaller share of its step.
- **Prefill is where the two diverge most**: 715 tok/s against 2.39k. The dense model has to multiply
  every weight for every prompt token; the A4B multiplies the routed experts only.
- **Draft count follows acceptance, not size.** Four drafts beat three on the 31B (54.1 to 52.8,
  acceptance 54.5% against 65.4% but a wider verified batch per weight read).

## A note on earlier figures

Measurements taken on this card before its power cap was lifted read 674 tok/s prefill and 48.8 /
49.7 tok/s decode for the 31B, with three drafts looking better than four. The cap, not the draft
count, produced that ordering: with the limit at its default 250 W the same configuration measures
715 tok/s prefill and 54.1 tok/s decode with four drafts. The tables above supersede those figures.
